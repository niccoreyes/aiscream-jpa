HAPI FHIR / OPERATIONS GUIDE

Local HTTPS.
From startup to shutdown.

One configured URL for the browser, the FHIR API and the tester. How Caddy, Docker and the scripts fit together.

A practical guide to starting, stopping and reproducing the HAPI FHIR demo environment with Docker Desktop and Caddy on macOS. Prepared 7 November 2026 from the current repository scripts.

Run ./up.sh to prepare local HTTPS and start HAPI. Run ./down.sh to stop the stack and reverse the recorded system changes. Both the tester target and the advertised FHIR base use one configured URL.

The tester makes a second request

The HAPI homepage fetches /fhir/metadata from inside its Java container. Docker maps the configured hostname to host-gateway, allowing that request to reach Caddy on the Mac. Java trusts Caddy through a mounted truststore. Browser trust and Java trust are separate.

Why the original warning appeared

The tester resolved phcore.thomasreyes.ph to 127.0.0.1 inside its container and tried port 443 there. That loopback address referred to HAPI itself, where no HTTPS listener existed. Hostname routing and Java CA trust fix that request while retaining the displayed HTTPS URL.

01 / GUIDE

Startup architecture

HTTP branch

Without LOCAL_HTTPS=true, the script uses the base Compose file. It still rebuilds the interceptor and waits for metadata. The default FHIR URL is http://localhost:8080/fhir. A leftover local HTTPS hostname marker causes an explicit stop: run down.sh before switching modes.

Caddy conditions

If the admin API on localhost:2019 responds, the script accepts only one server with one route matching the requested hostname. It saves the original JSON config and loads a simple loopback proxy. This is a coarse compatibility check, not a general merge of custom Caddy settings.

Otherwise it starts its own Caddy on admin port 2020, unless its recorded process is already alive. A conflicting listener on port 443 stops setup. Its own process is started in the background, so a separate Caddy terminal is unnecessary.

02 / GUIDE

Shutdown architecture

Removed or restored Preserved
Project containers and network hapi.postgress.data and Maven cache named volume
Owned hosts entry and active markers Pre-existing hosts entries and .env
Owned Caddy process or saved live config Caddy installation and macOS certificate trust
Generated Java outputs only if confirmed Local CA material and truststore for the next start

If cleanup fails

The script stops at the failed command. For example, an unreachable original Caddy admin API can prevent later hosts cleanup. Fix that dependency and rerun down.sh. Keep .local-https until cleanup completes; its files identify which changes belong to this setup.

03 / GUIDE

Repeat the setup on another Mac

1 Prepare the prerequisites

Install and start Docker Desktop. Install Caddy, Python 3 and a Java installation with keytool. The scripts also use standard macOS tools such as curl, lsof, sed and ps. No dependencies are installed automatically.

cd /path/to/aiscream-jpa
cp .env.example .env

2 Edit the local environment

FHIR_PUBLIC_URL=https://demo.example.test/fhir
FHIR_TESTER_NAME="FHIR Demo"
LOCAL_HTTPS=true

Use a valid hostname and the exact /fhir path. Local HTTPS accepts the default HTTPS port or explicit port 443. It rejects query strings, fragments and usernames. The URL does not change public DNS.

3 Start and trust the browser certificate

./up.sh

Respond to sudo locally if prompted. The script may need administrator access to start Caddy on port 443, read its CA certificate or append a hosts entry. It never stores a sudo password.

For a new CA, import .local-https/root.crt into Keychain Access and enable SSL trust for that certificate. Java trust is already prepared by the script. For a CA already trusted on this Mac, set CADDY_STORAGE to its existing data folder before starting.

CADDY_STORAGE="/Users/yourname/Library/Application Support/Caddy"

4 Confirm the result

Wait for Ready, open the homepage URL without /fhir, and check that FHIR Base shows the configured HTTPS URL and the conformance warning is absent. The first startup can take time while packages load.

5 Stop or change the URL

./down.sh
# Edit .env after shutdown, then restart
./up.sh

Plain HTTP: set LOCAL_HTTPS=false and FHIR_PUBLIC_URL=http://localhost:8080/fhir. An externally managed HTTPS proxy also uses LOCAL_HTTPS=false, but its URL must still be reachable and trusted by the tester inside Docker.

04 / GUIDE

Configuration and file ownership

Setting Purpose and default
FHIR_PUBLIC_URL Single URL for the API and tester. Default http://localhost:8080/fhir.
FHIR_TESTER_NAME Tester display name. Default Local FHIR.
LOCAL_HTTPS Exactly true enables the macOS local HTTPS branch. Default false.
CADDY_STORAGE Optional existing CA storage. Default repository .local-https/caddy.
FHIR_HOST Derived from the URL by up.sh and exported for the Compose override.

How the URL reaches HAPI

.env → up.sh exports → Compose environment → application.yaml

hapi.fhir.server_address
  ${FHIR_PUBLIC_URL:http://localhost:8080/fhir}
hapi.fhir.tester.home.server_address
  ${FHIR_PUBLIC_URL:http://localhost:8080/fhir}
Repository file Responsibility
up.sh and down.sh Root-level startup and cleanup entry points; no command-line flags.
docker-compose.yml HAPI, PostgreSQL, interceptor builder and URL environment variables.
compose.caddy.yaml Hostname to host-gateway mapping; read-only Java truststore mount; JVM options.
application.yaml HAPI public URL, tester URL and tester name placeholders.
.env.example Shareable configuration example. Copy to ignored .env locally.
Caddyfile Original manual reference. Scripts generate .local-https/Caddyfile at runtime.
README.md and .gitignore Operating instructions; exclude .env and generated HTTPS state.

Generated state is local

.local-https contains hostname, Caddyfile, PID or original config, root.crt, cacerts and diagnostics. hosts-entry exists only when the script added a tagged line. CA storage can contain private keys: do not commit or share it. HAPI mounts only cacerts, not the CA private key.

The .env file is sourced as shell code. Keep assignments shell-compatible, quote values containing spaces, and inspect any .env obtained from another person before using it.

05 / GUIDE

Troubleshooting and recovery

Symptom What to check
Conformance connection refused to 127.0.0.1:443 Start through up.sh with LOCAL_HTTPS=true. A plain Compose start omits the hostname override and JVM truststore.
Java certificate or PKIX error Verify root.crt belongs to the active Caddy CA. Check CADDY_STORAGE, then rerun up.sh to regenerate cacerts.
Browser certificate warning Trust the exact local CA in Keychain, or reuse its existing CADDY_STORAGE. Browser trust does not follow Java trust.
HTTP 502 during startup Wait for HAPI package loading. Inspect docker compose logs --tail=100 fhir. A running container is not necessarily a ready API.
Port 443 already in use Check the listener. Stop the intended conflicting process; do not terminate unrelated services.
Caddy admin API times out Check process state. A suspended process may retain its port. Resume or restart the intended Caddy instance.
Hostname or mode change rejected Run down.sh first. It clears the active hostname marker after cleanup.
Permission denied or sudo prompt Run from an interactive terminal and provide your own local administrator credentials.

Useful commands

docker compose ps
docker compose logs --tail=100 fhir
curl -fsS http://localhost:8080/fhir/metadata
curl --cacert .local-https/root.crt -fsS \
  https://your-hostname/fhir/metadata
lsof -nP -iTCP:443 -sTCP:LISTEN
ps -axo pid,state,command | rg caddy

Known boundaries

The local HTTPS script targets macOS with Docker Desktop. Linux and Windows were not implemented or tested. Custom API paths and HTTPS ports other than 443 are not supported by the URL validation. Existing hosts entries are preserved even if their address is unsuitable; inspect them if routing still fails.

Cleanup does not uninstall Caddy, remove CA files or revoke manual Keychain trust. Startup and shutdown are sequential operations with no transaction or rollback. If a command fails midway, retain the state directory, diagnose the failure and rerun the appropriate script.

06 / GUIDE

Changes and verification record

What changed

The previous configuration hardcoded the public hostname in two HAPI settings and required manual Caddy setup. The implementation introduced shared environment settings, an optional Compose override, a container truststore, recorded system changes and ordinary up/down commands. The existing Maven builder ordering is retained. Normal shutdown no longer offers to delete PostgreSQL data.

Observed on 7 November 2026

The HTTPS homepage rendered successfully with Server PH Core and the HTTPS FHIR Base. Its embedded CapabilityStatement loaded; Failed to load conformance statement, HAPI-1361 and Connection refused were absent. The metadata endpoint returned a CapabilityStatement advertising https://phcore.thomasreyes.ph/fhir. Shell syntax, Compose configuration and git diff whitespace checks passed.

The stack was stopped and restarted with persistent data retained. A suspended manually launched Caddy was replaced with a background instance using the existing trusted CA. The final admin API shutdown implementation and newly created hosts-entry cleanup branch were reviewed, but were not exercised in a separate complete final down/up cycle. Browser certificate trust was not modified.

Maintenance

When a script changes, update this guide and repeat the checks on the preceding pages. Keep the local environment and private CA material outside version control. This document is an operating guide for a local demo, not a production deployment design.

PUBLISHING

Keep this guide repeatable

GitHub Pages serves the main branch from /docs. Edit docs/index.html or docs/guide.css, commit, and push. No package installation or build step is needed.

git add docs/index.html docs/guide.css
git commit -m "Update local HTTPS guide"
git push origin main

Pages hosts only this documentation. It does not run HAPI, Caddy or the database. Your local FHIR endpoint still depends on your Mac and the scripts.
